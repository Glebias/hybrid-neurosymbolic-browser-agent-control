# Дизайн Browser Guard: рабочее пространство задач

Дата исследования: 02.11.2026. Статический макет — [browser-guard-concept.html](browser-guard-concept.html). Все его данные вымышлены; подключений к агенту, ключам и API нет. Файлы приложения не изменены.

## Основное решение

Панель строится вокруг выбранной задачи. Слева — история запусков, в центре — поручение, результат и действия. Контекст действия открывается по запросу. Новая задача — компактное действие, а не самая большая карточка при просмотре результата. Вместо четырёх глобальных KPI достаточно одной строки итогов конкретного запуска. Это дизайнерский выбор для текущего объёма MVP.

Две колонки, 270–280 px + оставшееся пространство, оставляют место для объяснений. Постоянная третья колонка сейчас избыточна; контекст можно раскрывать внутри действия либо в доступном диалоге. На телефоне выбор задачи должен оставаться доступным через компактный список/панель, а не исчезать.

## Что переносить в React в первую очередь

1. Убрать рекламные надзаголовки, повторяющийся подзаголовок и четыре счётчика со всех страниц. Названия разделов: «Задачи», «Подтверждения», «Правила», «Журнал».
2. Сделать список задач сканируемым: человекочитаемое начало поручения, состояние, дата; адрес вторичным текстом. URL в начале цели не должен занимать всё название. Исходную цель показывать полностью в выбранной задаче.
3. Вместо большой карточки агента использовать компактную строку: название, состояние, проверена ли интеграция. Модели запуска показывать в свойствах конкретной задачи; текущий маршрут настройки — отдельно.
4. У действия есть два разных факта: решение защиты и состояние исполнения. Например «Разрешено · исполнение не подтверждено» нельзя превращать в успешную зелёную галочку. При BLOCK явно писать «Не исполнялось».
5. В контексте первым показывать причину, адрес/получателя, тип данных, правило и результат удержания. Снимок — ниже, необработанный JSON — в последнем раскрытии. Блокировку не оформлять как техническую ошибку сервиса.
6. ASK_USER — отдельное выделенное ожидание с конкретным действием, данными, причиной, сроком. Кнопки «Разрешить это действие» и «Отказать»; никаких расплывчатых «Продолжить».
7. Редактор правила должен собирать предложение: «Если [признак] равен [значению], [исход]». Значения инструментов/эффектов выбирать из словаря; для origin сохраняется обычное поле адреса. Нужны пояснение применения к будущим действиям и отдельное отображение обязательных запретов.

## Визуальные параметры

Системный шрифт Segoe UI / Inter / sans-serif без внешнего запроса шрифта. Основной текст 15 px с межстрочным 1,55; вторичный 13 px, технический минимум 12 px; заголовок 24 px. Интервалы 8/12/16/24/32 px. Фон `#f6f7f9`, поверхность `#fff`, текст `#192431`, вторичный `#5b6878`, границы `#dfe4ea`. Синий акцент `#3157d5` применяется к основному действию и выбору. Состояния: зелёный `#17634a`, красный `#a42c33`, янтарный `#845800`; цвет всегда сопровождается словом/значком. Скругления 6–8 px, без градиентов и больших декоративных теней. Кнопки 40 px, на touch 44 px.

## Источники и что из них применено

- [LangSmith: View traces](https://docs.langchain.com/langsmith/view-traces) разделяет обзор траектории и подробный разбор конкретного запуска. Отсюда обзор действий с сохранением контекста задачи, затем углубление в выбранное действие. Полные рассуждения агента для Browser Guard не требуются.
- [Carbon: Data table](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines) описывает раскрываемые строки для подробностей, общую панель фильтров и согласованные размеры. В журнале пригодна таблица с раскрытием/диалогом, в ходе задачи — последовательность действий. Не копировать всю корпоративную дизайн-систему.
- [GOV.UK: Details](https://design-system.service.gov.uk/components/details/) рекомендует скрывать вторичные сведения, сохраняя важные видимыми. Причина отказа видна сразу; технический JSON раскрывается.
- [GOV.UK: Panel](https://design-system.service.gov.uk/components/panel/) использует выделение для подтверждения результата или прерывания процесса. Отсюда сдержанное выделение результата/ожидания, а не превращение каждого блока в яркую карточку.
- [Atlassian: Lozenge](https://atlassian.design/components/lozenge) задаёт семантические состояния компактных меток. В Browser Guard метки имеют постоянные значения и не обрезаются ради декоративной ширины.
- [W3C: Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) задаёт минимальную цель 24×24 CSS px с исключениями. Практический выбор макета — 40–44 px для основных действий, видимый фокус и текстовые названия.

Референсы использованы как паттерны взаимодействия. Геометрия, композиция, палитра и тексты макета — предложение под конкретный проект, а не утверждение о единственном «лучшем» интерфейсе.

## Критерии приёмки

При 1440×1000 выбранная задача, результат и начало действий видны без большой зоны рекламного текста. При 760 px доступен выбор задачи; при 390 px нет горизонтального скролла. Увеличение до 200% не скрывает кнопки согласия/отказа. Контекст закрывается Escape с возвратом фокуса. Отсутствие соединения показано состоянием сервиса, а не зелёным декоративным индикатором. Обновление событий не перебрасывает выбранную задачу и не меняет решение пользователя.
